## Overview

The Fee Manager allows you to configure the parameters of the dynamic fee algorithm on-chain. This gives you control over:

- Gas limits
- Base fee parameters
- Fee configuration changes at runtime, without a network upgrade

| Property | Value |
|----------|-------|
| **Address** | `0x0200000000000000000000000000000000000003` |
| **ConfigKey** | `feeManagerConfig` |

## Configuration

You can activate this precompile in your genesis file:

```json
{
  "config": {
    "feeManagerConfig": {
      "blockTimestamp": 0,
      "adminAddresses": ["0x8db97C7cEcE249c2b98bDC0226Cc4C2A57BF52FC"],
      "initialFeeConfig": {
        "gasLimit": 20000000,
        "minBaseFee": 1000000000,
        "targetGas": 100000000,
        "baseFeeChangeDenominator": 48,
        "targetBlockRate": 2,
        "minBlockGasCost": 0,
        "maxBlockGasCost": 10000000,
        "blockGasCostStep": 500000
      }
    }
  }
}
```

<Callout type="warn">
**Deprecated by the Granite upgrade**

`targetBlockRate`, `minBlockGasCost`, `maxBlockGasCost` and `blockGasCostStep` fed the block gas cost formula. From Granite onward the block gas cost is always zero, so these values no longer influence fees.

**They are still required.** Configuration validation rejects a config in which any of them is missing, and the node will refuse to start. Keep them in your genesis and leave them at their current values. They also remain in the `IFeeManager` interface so that chains activated before Granite can replay their historical blocks.
</Callout>

## Fee Parameters

### Active

| Parameter | Description | Recommended Range |
|-----------|-------------|------------------|
| `gasLimit` | Maximum gas allowed per block | 8M - 100M |
| `minBaseFee` | Minimum base fee, in wei | 25 - 500 gwei |
| `targetGas` | Target gas spending over the last 10 seconds | 5M - 50M |
| `baseFeeChangeDenominator` | Controls how quickly the base fee changes. A larger value makes the fee stickier | 8 - 1000 |

`minBaseFee` accepts `0`. A value of zero means transactions on the chain carry no network fee, which is a supported configuration for a permissioned venue that recovers its costs elsewhere.

### Deprecated by Granite, still required

| Parameter | Former role | What to set |
|-----------|-------------|-------------|
| `targetBlockRate` | Target seconds between blocks, used in the block gas cost formula | Keep current value |
| `minBlockGasCost` | Minimum gas cost charged for producing a block | Keep current value |
| `maxBlockGasCost` | Maximum gas cost charged for producing a block | Keep current value |
| `blockGasCostStep` | How fast the block gas cost changed per second of deviation | Keep current value |

## Interface

```solidity
interface IFeeManager {
  struct FeeConfig {
    uint256 gasLimit;
    uint256 targetBlockRate;
    uint256 minBaseFee;
    uint256 targetGas;
    uint256 baseFeeChangeDenominator;
    uint256 minBlockGasCost;
    uint256 maxBlockGasCost;
    uint256 blockGasCostStep;
  }
  
  event FeeConfigChanged(address indexed sender, FeeConfig oldFeeConfig, FeeConfig newFeeConfig);

  function setFeeConfig(
    uint256 gasLimit,
    uint256 targetBlockRate,
    uint256 minBaseFee,
    uint256 targetGas,
    uint256 baseFeeChangeDenominator,
    uint256 minBlockGasCost,
    uint256 maxBlockGasCost,
    uint256 blockGasCostStep
  ) external;

  function getFeeConfig() external view returns (
    uint256 gasLimit,
    uint256 targetBlockRate,
    uint256 minBaseFee,
    uint256 targetGas,
    uint256 baseFeeChangeDenominator,
    uint256 minBlockGasCost,
    uint256 maxBlockGasCost,
    uint256 blockGasCostStep
  );

  function getFeeConfigLastChangedAt() external view returns (uint256 blockNumber);
}
```

The interface keeps all eight fields, including the deprecated ones, so that `setFeeConfig` remains ABI-compatible with contracts written before Granite.

## Access Control and Additional Features

The FeeManager precompile uses the [AllowList interface](/docs/avalanche-l1s/precompiles/allowlist-interface) to restrict access to its functionality.

In addition to the AllowList interface, the FeeManager adds:

- `getFeeConfig`: retrieves the current dynamic fee config. Readable by anyone.
- `getFeeConfigLastChangedAt`: retrieves the **number of the block** in which the fee config was last updated. Returns `0` if it has never been changed. Readable by anyone.
- `setFeeConfig`: sets the dynamic fee config on chain. Callable by `Admin`, `Manager` and `Enabled` addresses.
- `FeeConfigChanged`: an event emitted when the fee config is updated. Topics include the sender; the data carries the old and the new fee config.

You can also read the fee configuration at a given block with the `eth_feeConfig` RPC method. For more information see [here](/docs/rpcs/subnet-evm#eth_feeconfig).

## Best Practices

1. **Fee Configuration**:
   - Test fee changes on a testnet first
   - Monitor network congestion and adjust accordingly
   - Document the rationale for fee parameter changes
   - Announce changes to validators in advance
   - Read back the config with `getFeeConfig` after every change, and record the block number from `getFeeConfigLastChangedAt`

2. **Security Considerations**:
   - Use a multi-sig for admin addresses
   - Watch `FeeConfigChanged` events for unauthorized changes
   - Have a plan for fee parameter adjustments
   - Keep a backup of previous configurations
